Część I · Czym jest Avro?

Czym jest Avro?

System serializacji danych rekordowych. Projekt Apache, stworzony w 2009 r. przez Douga Cuttinga. Serializacja to zamiana obiektu z pamięci na bajty i z powrotem.

SCHEMAJSON: struktura i typy pól
+
DANEbinarne, same wartości
=
AVRO

Wymiana danych

Wiadomości w Kafce i data streaming. Najpopularniejsze zastosowanie.

Format plików

Pliki .avro w Hadoop, Spark, data lake i hurtowniach w chmurze.

RPC

Wywoływanie metod na innym serwerze. Avro opisuje metody usługi, a argumenty i wyniki przesyła w formacie Avro.

Część I · Kluczowa idea

Dane nie zawierają nazw pól

Ten sam rekord {age: 2} zapisany w trzech formatach:

FormatBajtyRozmiarCo jest zapisane

Skoro w bajtach nie ma nazw ani typów, reader musi znać schemat, którym dane zostały zapisane: writer's schema.
Część I · Jak to wygląda

Ten sam pracownik: JSON vs Avro

JSON · 40 bajtów (bez spacji)
{
  "firstName": "Ala",
  "age": 2,
  "email": null
}
Avro · 6 bajtów
06416C61 0400
firstNameageemail
Reader idzie po schemacie jak po skrypcie
06416C61

string: najpierw długość 06 = 3, potem 3 bajty UTF-8 → "Ala"

04

int: 04 → 2 (zigzag encoding)

00

union: indeks gałęzi 0 → null, sama wartość zajmuje 0 B

Ta sama wartość bajtu może znaczyć coś innego. O znaczeniu decyduje pozycja w schemacie. Długość stringa jest zapisana przed treścią, więc nie trzeba znaku końca.
Część I · Kodowanie liczb

Zigzag encoding

int i long mają zmienną długość: małe liczby zajmują 1 bajt. Żeby małe były też liczby ujemne, Avro przeplata liczby dodatnie i ujemne.

Wartość01−12−23−3…
Zapisane jako0214365…

Wartość dodatnia n staje się 2n, ujemna staje się nieparzysta. Nasze age = 2 to bajt 04.

Większe liczby zajmują więcej bajtów. Rozmiar zależy od wartości, a nie od typu, dlatego Avro nie potrzebuje typów short ani unsigned.

Część II · Schema

Anatomia schematu

src/main/resources/avro/employee.avsc
{
  "type": "record",                            ①
  "name": "Employee",                          ②
  "namespace": "com.example.avro.generated",
  "doc": "Pracownik firmy",
  "fields": [                                  ③
    {"name": "firstName", "type": "string"},
    {"name": "age",       "type": "int"},
    {"name": "email", "type": ["null", "string"],
     "default": null}                           ④
  ]
}
  1. record: typ złożony z nazwanymi polami.
  2. name + namespace = pełna nazwa com.example.avro.generated.Employee, używa jej generator klas.
  3. kolejność pól = kolejność bajtów w danych.
  4. union z null + default: pole opcjonalne.
doc, default, aliases nie zmieniają bajtów. Służą dokumentacji i schema evolution.

Część II · Typy

Typy złożone

record

Pola po kolei, bez nagłówka i separatorów.

{"type":"record", "fields":[…]}

enum

Indeks symbolu jako int.

"symbols":["IT","HR","SALES"]
HR → 02

array

Liczba elementów, potem kolejne elementy.

{"type":"array", "items":"string"}

map

Jak array, ale pary klucz + wartość.

{"type":"map", "values":"int"}

fixed

Dokładnie N bajtów, bez długości.

{"type":"fixed", "name":"Md5", "size":16}

union

Jedna z kilku gałęzi: indeks gałęzi + wartość.

["null","string"] → następny slajd

Część II · Typy

Union i null: pola opcjonalne

{"name": "email", "type": ["null", "string"], "default": null}
email = null → 1 bajt
00

indeks 0 → gałąź "null", wartość: 0 bajtów

email = "a@b.pl" → 8 bajtów
020C6140622E706C

indeks 1 → gałąź "string", potem długość 6 i znaki

  • W danych zapisany jest indeks gałęzi, więc reader wie, którego typu użyć.
  • Brak wartości kosztuje 1 bajt.
  • default musi pasować do pierwszej gałęzi, więc przy default: null typ "null" idzie pierwszy.
  • Union nie może mieć dwóch gałęzi tego samego typu (wyjątek: różne typy nazwane, np. dwa rekordy).

Część II · Schema evolution

Schema evolution: schemat też się zmienia

Historia jednego schematu

v1

firstName, age, email

v2

+ department z default: "IT"

v3

age: int → long

v4

firstName → givenName

Wymagania się zmieniają: dochodzą pola, inne znikają, typy rosną, nazwy się poprawia.

Problem

  • Producenci i konsumenci są wdrażani niezależnie. Nie da się zaktualizować wszystkich naraz.
  • Dane żyją długo: topic w Kafce (retencja), pliki w data lake. Stare i nowe dane leżą obok siebie.
  • W bajtach nie ma nazw pól, więc kod nie zgadnie sam, co się zmieniło.
Rozwiązanie Avro

1. Bajty dekodujemy writer's schema, czyli schematem, którym je zapisano.

2. Wynik dopasowujemy do reader's schema, czyli schematu, którego używa nasz kod.

3. Schema Registry odrzuca nową wersję schematu, która nie jest compatible.

Type promotion

Niedozwolone, np. int → string, double → float, long → int. Obejście: nowe pole + default.

Przykład: age int → long
04
zapisane jako int → czytane jako long → 2

Bajty są identyczne: oba typy używają tego samego kodowania o zmiennej długości. Rośnie tylko zakres.

nowy (long) czyta stare (int)✓ BACKWARD
stary (int) czyta nowe (long)✗ FORWARD
Uwaga na precyzję: long → double jest dozwolone, ale double ma ~16 cyfr znaczących, a long ~19.

Część II · Schema evolution

Zmiana nazwy pola

W bajtach nie ma nazw, a dopasowanie odbywa się po nazwie. Zwykła zmiana nazwy = usunięcie starego pola + dodanie nowego.

Bez aliasu ✗

{"name": "givenName", "type": "string"}

Stare firstName zostaje odrzucone, a givenName nie ma wartości domyślnej, więc błąd (albo cicha utrata danych, jeśli default jest).

Z aliasem ✓

{"name": "givenName", "type": "string",
 "aliases": ["firstName"]}

Reader dopasuje stare firstName do nowego givenName.

Alias jest w reader's schema, więc pomaga tylko w kierunku BACKWARD. Stary konsument nie wie, że givenName to jego firstName.
Część III · Avro + Kafka

Gdzie jest schema w Kafce?

Topic to miliony małych wiadomości o tym samym kształcie. Doklejenie schematu do każdej z nich zniweczyłoby całą kompaktowość. Zamiast tego wiadomość niesie ID schematu.

Format wiadomości Confluent (Schema Registry) · 11 bajtów
00 00000001 06416C610400
magic byteID schematu (4 B)dane Avro (te same 6 B)
Alternatywa ze specyfikacji Avro, single-object encoding: C3 01 + 8-bajtowy fingerprint schematu + dane. Fingerprint liczony jest z kanonicznej postaci schematu, więc nie potrzeba centralnego licznika ID.

Podsumowanie

Co warto zapamiętać

1

Dane bez nazw pól, więc reader potrzebuje writer's schema.

2

Kompaktowe liczby (zigzag encoding, zmienna długość): rozmiar zależy od wartości.

3

Schema evolution: dekodowanie wg writer's schema, dopasowanie po nazwie; default, aliases, type promotion.

4

Kafka + Schema Registry: ID schematu w wiadomości, compatibility check przy rejestracji.

5

Avro do data streaming i wymiany danych, Parquet do analityki. Razem w jednym pipeline.
